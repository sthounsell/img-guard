# Expose the Rust core to Node via WebAssembly

Status: accepted

Radu's brief specified WebAssembly as the delivery mechanism for the Rust core, consumed from Node via `wasm-pack --target nodejs`. We considered and rejected `napi-rs` (a native Node addon) as an alternative.

## Considered Options

- **napi-rs native addon**: would give true native speed and full `std` access (no wasm sandbox), and is the more common choice for Node-only, performance-critical Rust integrations in the wider ecosystem. Rejected because it's Node-only (needs a separately compiled binary per OS/architecture) and the brief specifically asked for WebAssembly — likely because the client's real architecture wants portability beyond Node.
- **WebAssembly via wasm-bindgen** (chosen): the same compiled artifact can run in Node, a browser, or other WASM hosts unchanged, and its sandboxing (no filesystem, no arbitrary syscalls) reinforces the side-effect-free design in ADR 0001 for free.

## Open Questions

- **Is WebAssembly a hard requirement, or a default we chose absent a stated constraint?** (raised 2026-08-21) If portability beyond Node was never actually load-bearing for the client's real use case, napi-rs's native speed may be worth the per-OS/arch build cost after all. Raised with Radu; this ADR's "accepted" status stands until he answers. Still unanswered.
- **Benchmarking** — resolved 2026-08-27, verbally, in person: Radu's four links (2026-08-21 Slack — [`phash`](https://npmx.dev/package/phash), [`@stabilityprotocol.com/phash`](https://npmx.dev/package/@stabilityprotocol.com/phash), [`bktree-fast`](https://npmx.dev/package/bktree-fast), [`sharp-phash`](https://npmx.dev/package/sharp-phash)) weren't narrowing to one named baseline — he wants img-guard benchmarked against each of the four. Simon had read the ask as "tell me which one is the baseline" and was waiting on an answer; Radu, following up this morning, indicated the four were already the answer. No single "existing Node solution" to compare against — it's a benchmark matrix across all four (`bktree-fast` is a BK-tree search structure rather than a phash implementation, so it may need pairing with one of the others rather than standing alone).
- **Benchmark outcome** — recorded 2026-08-27, issue #12/#19: full comparison and methodology in `benchmarks/results/comparison.md`. Compute-axis steady-state cost doesn't show the WASM boundary as an obvious drag on img-guard — it's competitive at small/medium image sizes and only meaningfully behind `sharp-phash` (native) and `@stabilityprotocol.com/phash` (pure JS) at large ones, with all three confirmed at parity on hash bit-length (64-bit). That's weak evidence for `napi-rs` meaningfully improving compute performance on its own. The much larger finding was on the lookup axis, not this ADR's axis at all: img-guard's linear-scan Store lookup is roughly an order of magnitude slower than a BK-tree (`bktree-fast`) at 10,000 entries — ~25x on steady-state query cost alone, ~12x once cold-start/build cost is folded in (corrected after a measurement-asymmetry bug in the original harness overstated it as ~2 orders of magnitude) — a Node-side data-structure choice, orthogonal to WASM vs. `napi-rs`. Doesn't resolve this ADR's open question (that's still Radu's call), but narrows what benchmarking can tell him: the case for `napi-rs` rests on portability/architecture reasoning, not on compute speed the numbers here show.
- **Second correction** — recorded 2026-08-27, issue #20: that "~25x/~12x slower than `bktree-fast`" lookup-axis figure conflated two effects. A third candidate (img-guard's phash entries in a plain array, same algorithm, no SQLite) isolated them: at 10,000 entries, ~17x of the ~33x steady-state gap is SQL query-engine overhead, only ~2x is genuinely the linear-scan-vs-BK-tree algorithm (comparison.md's "SQL overhead vs. algorithmic gap"). Strengthens this ADR's own compute-axis conclusion by extension — the lookup-axis bottleneck was never a WASM/native-binding question either, and now not even mainly an algorithm question; it's a SQL-vs-in-memory-structure choice, orthogonal to both this ADR's WASM-vs-`napi-rs` question and to whether a BK-tree specifically gets adopted.
- **Third correction — real-world images** — recorded 2026-08-27, issue #21: the "Benchmark outcome" bullet's compute-axis conclusion above was based only on synthetic BMP squares up to 4096x4096. Run against 4 of Radu's own sample photos (4898x3265 up to 9504x6336) instead, img-guard's gap against `sharp-phash` at large sizes is bigger than the synthetic sweep implied — 3.85x-8.31x, not ~1.9x — and the cause is now identified rather than assumed: JPEG supports shrink-on-load (a compressed-stream-aware decoder can produce a downscaled image directly, far cheaper than full-resolution decode), which `sharp-phash`'s libvips backend exploits and img-guard's `image`-crate decoder has no equivalent for — every call pays full-resolution decode cost regardless of how much detail phash's 8x8 DCT grid actually needs. This matters for this ADR specifically: it's a real, structural decode-path gap that a `napi-rs` rewrite on the *same* `image` crate would inherit unchanged — the fix, if this is worth pursuing, is a JPEG decoder with fractional/shrink-on-load decoding (however Rust reaches Node), not the WASM-vs-native-binding boundary this ADR is actually about. Full detail in `benchmarks/results/comparison.md`'s "Real-world images" section. Still doesn't resolve this ADR's open question on its own — but it does mean "img-guard is only meaningfully behind at large sizes" understated both how large that gap gets and why, on real files rather than synthetic ones.
